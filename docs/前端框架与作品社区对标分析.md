# 前端框架与作品社区对标分析

研究日期：2026-10-04。框架能力与产品功能依据官方文档、官方源码或产品公开页面；本项目现状依据当前工作区，包含尚未提交的画廊改版，不等同于线上已经发布的状态。框架适用性与优先级是工程判断，不是性能跑分结果；不推测参考网站技术栈，也不把“AI 拟人题材”视为“AI 生成内容”。

## 1. 选型结论

**当前“蓝色大肥鱼”最适合继续使用 Astro。** 作品、角色、分类、专题和详情页主要面向公开浏览，内容通过审核与构建发布，已有静态页面和图片分仓流程。Astro 的静态输出和按需交互组件契合这种内容展示方式，迁移框架目前缺少足够收益。[Astro islands](https://docs.astro.build/en/concepts/islands/)、当前构建配置

当搜索筛选、批量收藏、上传表单等区域开始出现较复杂的共享状态时，可以采用 **Astro + 一种 React、Vue 或 Svelte 交互组件**，逐步替换相应区域。Astro 支持这些组件按 `client:*` 指令加载；能够混用多个 UI 框架，不代表项目需要混用。[Astro 框架组件](https://docs.astro.build/en/guides/framework-components/)、[islands 加载方式](https://docs.astro.build/en/concepts/islands/)

如果以后账号、同步收藏、关注、通知、实时投稿与个性化内容成为主体验，再重点比较 **Next.js、Nuxt、SvelteKit，以及 React Router Framework Mode**。现有后台采用 Next + React，给 React 路线带来团队知识复用的可能；熟悉 Vue 的团队可优先 Nuxt，熟悉 Svelte 的小团队可考虑 SvelteKit。选择应依据团队经验、状态复杂度和部署要求，不能仅凭网站像 pixiv 就迁移。[React 框架选型](https://react.dev/learn/creating-a-react-app)、[Nuxt 简介](https://nuxt.com/docs/4.x/getting-started/introduction)、[SvelteKit 页面选项](https://svelte.dev/docs/kit/page-options)、后台依赖

这也不是“完整社区必须搬走 Astro”的硬性边界：公开页面可以继续静态生成，动态个人区域接独立 API；确实需要按请求生成 HTML 的部分，也可以为 Astro 添加 adapter。只有维护一套共享应用状态与路由的收益持续大于迁移成本时，才值得迁移公开前端。[Astro 按需渲染](https://docs.astro.build/en/guides/on-demand-rendering/)

| 观察到的现状 | 对选型的意义 | 本地依据 |
| --- | --- | --- |

| `admin/` 使用 Payload + Next + React，不参与公开前端构建 | 后台与公开展示站可以采用不同框架，没有统一框架的必然要求 | 后台依赖、仓库说明 |
| 作者专题已实现作者介绍与联系渠道；角色页已有角色与类型组合的作品聚合 | 重点是完善内容和浏览关联，已有能力不必从零重做 | 作者组件、角色页 |
| 中文默认，英文、日文由页面脚本切换，尚无三语独立内容 URL | 国际化页面索引是独立设计问题，不能由换框架自动解决 | 语言脚本、公共布局 |

## 3. 先分清“组件框架”和“站点应用框架”

React、Vue、Svelte、Solid 主要提供 UI 组件与状态表达方式；Angular 则包含路由、表单、依赖注入等更完整的应用能力。Astro、Next.js、Nuxt、SvelteKit，以及 React Router 的 Framework Mode，进一步处理页面路由、数据加载、渲染和部署。**“Astro 和 React 哪个更好”并不是单一层面的二选一，Astro 可以直接使用 React 组件。**[React 新应用](https://react.dev/learn/creating-a-react-app)、[Vue 使用方式](https://vuejs.org/guide/introduction.html)、[Svelte 与 SvelteKit](https://svelte.dev/docs/svelte/overview)、[Angular 能力](https://angular.dev/overview)、[Astro 框架组件](https://docs.astro.build/en/guides/framework-components/)

另一组概念也要分开：SSG 在构建时生成 HTML，SSR 在请求时生成 HTML，CSR 在浏览器执行代码生成内容；SPA 描述浏览器内的导航和应用组织方式。支持 SSR 的应用也可以在后续访问中使用客户端路由，静态生成的页面也可以带交互组件。框架名称本身不能说明最终部署是否需要常驻服务器。[Vue SSR 与 SSG](https://vuejs.org/guide/scaling-up/ssr.html)、[Next 静态导出](https://nextjs.org/docs/app/guides/static-exports)、[SvelteKit 页面选项](https://svelte.dev/docs/kit/page-options)

### UI 层的优劣与场景

下面“优势”来自框架能力，“代价”和“适用场景”是针对本项目的判断，不是通用性能排名。

| UI 层 | 优势 | 需要承担的代价 | 适合的场景与本项目用途 |
| --- | --- | --- | --- |
| **React** | 声明式组件、状态和事件模型；可配合 Next 或 React Router 组织完整应用 | 仅选 React 仍需解决路由、数据获取和应用结构；服务端与浏览器代码边界需明确 | 复杂筛选、收藏管理、上传与社区交互；本项目已有 React 后台经验可复用。[官方选型说明](https://react.dev/learn/creating-a-react-app) |
| **Vue** | 渐进采用；单文件组件把模板、逻辑和样式放在一起；可从局部增强到完整应用 | 仍需设计共享状态、响应式依赖与路由；SSR 中要处理浏览器 API 和水合问题 | 表单、后台、筛选面板；习惯 HTML 模板的团队可用 Astro + Vue，完整社区可用 Nuxt。[Vue 简介](https://vuejs.org/guide/introduction.html)、[SSR 约束](https://vuejs.org/guide/scaling-up/ssr.html) |
| **Svelte** | 通过编译器处理 HTML/CSS/JS 组件，交互表达较直接；可与 SvelteKit 配套 | 需要学习其响应式与编译语义，并核验项目所需插件和组件的适配 | 图库控件、预览器、收藏面板；团队熟悉时可承担完整应用。[官方概览](https://svelte.dev/docs/svelte/overview) |
| **Angular** | 官方提供路由、表单、依赖注入、CLI，并支持 SSR/SSG | 当前小型内容站引入完整体系，会增加迁移与概念成本 | 多人维护、表单和权限流程繁多的业务系统；对当前公开画廊优先级较低，不能说它只能做 SPA。[官方概览](https://angular.dev/overview)、[混合渲染](https://angular.dev/guide/ssr) |
| **Solid** | signals 与细粒度响应式可以针对变化区域更新 | 需要理解依赖追踪；相似的 JSX 语法不代表能直接复用 React 组件，所需集成要逐项核验 | 对交互更新成本敏感的局部工具可以试点；当前没有仅因展示图片而引入它的必要。[细粒度响应式](https://docs.solidjs.com/advanced-concepts/fine-grained-reactivity) |

### 站点应用框架的优劣与场景

| 路线 | 优势 | 限制与成本 | 当前适配判断 |
| --- | --- | --- | --- |
| **Astro** | 静态 HTML 为默认方向，交互组件按需加载；能保留现有内容与发布流程 | 大量跨页面共享状态需要额外组织；构建期内容更新需要发布；按请求渲染需 adapter 和相应运行环境 | **当前首选。** 图库、角色图鉴、作者专题、多图作品、搜索和本地收藏都可继续实现。[islands](https://docs.astro.build/en/concepts/islands/)、[按需渲染](https://docs.astro.build/en/guides/on-demand-rendering/) |
| **Next.js + React** | Server Components 与 Client Components 可组合数据加载和交互；支持静态导出，也可使用动态服务端能力 | 需要理解两类组件边界、水合与缓存；纯静态导出不支持 cookies、Server Actions、ISR 和默认图片优化等服务器能力 | **完整社区的重点候选。** 适合 React 团队；只有增加动态能力时，才相应增加服务端部署要求。[组件边界](https://nextjs.org/docs/app/getting-started/server-and-client-components)、[静态导出限制](https://nextjs.org/docs/app/guides/static-exports) |
| **Nuxt + Vue** | 约定式组织与 Vue 组件；支持通用渲染、CSR，以及逐路由的混合渲染与缓存规则 | 需要处理水合、会话、缓存与服务端数据边界；`nuxt generate` 产物不包含 server endpoints，也不支持运行时混合渲染 | **Vue 团队的重点候选。** 适合公开作品页面和动态个人区域并存的应用。[简介](https://nuxt.com/docs/4.x/getting-started/introduction)、[渲染模式](https://nuxt.com/docs/4.x/guide/concepts/rendering) |
| **SvelteKit + Svelte** | 路由、取数和应用结构统一；可逐页控制 `prerender`、`ssr`、`csr`，通过 adapter 部署 | 默认仍会水合并启动客户端路由，不应把它当作默认零 JS；迁移收益取决于团队和所需组件适配 | **有 Svelte 经验时的备选。** 可做紧凑的作品社区，当前替换 Astro 的理由较弱。[页面选项](https://svelte.dev/docs/kit/page-options)、[静态 adapter](https://svelte.dev/docs/kit/adapter-static) |
| **React/Vue + Vite 的纯 CSR SPA** | 浏览器状态集中，适合登录后的管理、编辑、审核工具；可静态部署应用外壳 | 路由与数据层需组装；作品正文要等 JS 与数据请求后才出现，爬虫、分享预览、首屏和 JS 失败回退需要额外处理 | **适合后台或个人工具，不优先用于公开作品目录。** 问题在纯 CSR 模式，不能推导成 React/Vue 不适合 SEO。[React 从零构建](https://react.dev/learn/creating-a-react-app)、[Vue SSR 说明](https://vuejs.org/guide/scaling-up/ssr.html)、[SPA 取舍](https://svelte.dev/docs/kit/single-page-apps) |

React Router 的 Framework Mode 也是 React 应用候选：在路由数据能力上提供 Vite 集成、代码拆分与 SPA/SSR/静态渲染策略。研究 Remix 系路线时应一并参考官方 Remix v2 迁移说明，不必把 React Router 当成只能负责跳转的库。[模式说明](https://reactrouter.com/start/modes)、[Remix v2 迁移说明](https://reactrouter.com/upgrading/remix)

## 4. 作品题材与架构边界

框架不识别作品题材。“AI 拟人”影响角色、标签、来源和作品组织方式；架构选择取决于内容更新、交互状态和社区能力。本项目已有表情包、插画、设定、漫画四类内容；多图作品需要设计数据模型和 viewer，换框架不会自行产生这种能力。分类清单

性能与 SEO 应独立验收：检查 HTML 正文、图片与加载策略、索引体积、CDN、移动端内存、规范 URL、分享元数据与译文页面结构。SSG/SSR 能输出 HTML，不保证实际页面已经快或可发现。[Vue SSR/SSG 的取舍](https://vuejs.org/guide/scaling-up/ssr.html)、[Next 静态导出](https://nextjs.org/docs/app/guides/static-exports)

内容增长后，可以分别演进搜索 API、缓存与发布流程、图片存储和 CDN。迁移触发条件应是实测瓶颈，例如索引加载拖慢手机首屏、搜索响应不达标、构建时间无法满足发布频率，或跨页面状态长期难以维护；作品数量本身不是充分条件。

## 6. 按优先级推进，无需先换框架

| 优先级 | 应解决的问题 | 建议能力 | 对架构的影响 |
| --- | --- | --- | --- |
| **P0：找到、看清、保存** | 用户能否迅速找到角色作品、看懂来源、下载或收藏 | 搜索/筛选反馈；清晰的大图与详情；作者和出处；原图下载；本地收藏；移动端与返回浏览位置 | 在现有 Astro 与交互脚本上完成；先度量图片、搜索与滚动体验 |
| **P1：作品组织更完整** | 单张图片之外的角色、作者和系列是否易理解 | 完善角色图鉴与现有作者专题内容；标签别名；多图作品/设定集；相关作品；人工精选专题 | 重点是数据与模板；需要复杂状态时引入一种 UI island |
| **P2：形成持续社区** | 用户如何跨设备使用、投稿和获得反馈 | 身份体系；同步收藏；关注与通知；投稿进度；审核与持久化 API | 先定义 API、权限与数据模型，再决定个人区域或公开前端是否采用应用框架 |

社区功能的核心工作还包括身份、数据存储、图片处理、审核状态与通知等。Next/Nuxt/SvelteKit 能帮助组织页面和服务端入口，不能代替这些产品与后台能力的实现。
